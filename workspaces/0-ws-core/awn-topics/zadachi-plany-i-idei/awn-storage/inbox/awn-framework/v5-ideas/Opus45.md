## Общая оценка каркаса

Каркас — реально собран. Это не просто папки с заметками: видно, что есть концепция, контракты, команды и механизм сессий. Многие тратят месяцы и не доходят до того, что у вас уже есть. Дам прямую оценку — что сильно, что хромает, и где сейчас находитесь по жизненному циклу.

### Что получилось хорошо

**Концептуальная база.** Метафора клеток, слои Space/Part/Memory/View/External, разделение «нода = логика / память = опыт / external = сырьё» — это рабочая онтология, а не набор баззвордов. Она объясняет почти любой кейс без натяжки.

**Дизайн через суффиксы** (`*.node.md`, `*.documentation.md`, `*.configuration.md`, `*.combined.md`, `*.sidecar.md`, `*.volume.md`). Простой, читаемый, портативный. Любой агент или скрипт может работать с системой через glob-маски — это редкое преимущество. Tana и Capacities таким похвастаться не могут.

**Разделение полномочий по папкам:**

- `01 Core/` — то, что грузится в полной сессии (bootstrap-протоколы);
- `02 Components/` — описания компонентов системы;
- `03 Configs/`, `04 Templates/` — конфиг и шаблоны;
- `awn.*` в корне — системные сводки.

Это функциональное разделение, а не тематическое. Очень правильно.

**Полная vs чистая сессия** — лаконичный механизм. Слово-триггер («Привет»/«Hi») управляет уровнем загрузки контекста. Минимум инфраструктуры — максимум смысла.

**Команды как первоклассные сущности** («обнови документацию», «обнови реестр», «создай ноду», «запомни»). Это даёт агенту явный язык управления состоянием. Не «делай так, потому что я попросил», а «вот команда, у неё есть протокол».

**Принципы DRY/DDD/KISS/YAGNI/SRP/APO/BDUF/Occam в явном виде.** Я вижу мало knowledge-фреймворков, где базовые принципы инженерии прямо заявлены и применяются к организации заметок. Обычно это «как-то само сложилось».

**Подпапки с `_` префиксом** (`_Assets/`, `_Content/`, `_Parts/`) — хороший трюк: всегда наверху в сортировке, человеку понятна служебная природа.

**Volume как отдельный тип памяти** — это редкая идея: разделить «истину» (нода) и «контекст агента» (volume). Большинство систем смешивают.

### Где сейчас слабо (технический долг)

#### 1. Дрейф YAML-схемы — самый заметный долг

Три конвенции живут одновременно:

- **Старая:** `AWN-CORE-TYPE`, `AWN-CORE-CHILDREN-ALLOW`, `AWN-CORE-ROLE` (видна в `zzz 06 Intro ИЛИ REPO`)
- **Новая компонентная:** `AWN-SCHEMA`, `AWN-ID`, `AWN-SLUG`, `AWN-TYPE`, `AWN-ALLOW-CHILDREN`, `AWN-LAYER`, `AWN-NAME`, `AWN-DESC`, `AWN-REGISTRY` (большинство нод-папок)
- **Skeleton-Node:** `AWN-TITLE` (а не `AWN-NAME`), `AWN-DESC`, `AWN-LOAD`, `AWN-PRIORITY`, `AWN-STATUS`, `AWN-TRIGGERS`, `AWN-MEMORY`, `AWN-AUTOMATIZATION`…
- **`awn.settings.md` обещает:** `lower_snake_case` с префиксом `awn_` (типа `awn_type`, `awn_status`)

То есть **четыре** разных конвенции одновременно. До тех пор пока нет единой канонической схемы — реестры, валидаторы и команды будут работать на «магическом понимании».

#### 2. Конвенция именования файлов

`awn.settings.md` декларирует `kebab-case`, а на диске — «01 Workspace.documentation.md» и «01 CrudNode.documentation.md». Либо правило про kebab — мёртвое, либо в нодах должно быть `01-workspace.documentation.md`. Сейчас оно «выключено по умолчанию» (ни в одну сторону не применяется).

#### 3. Призраки в реестрах и кросс-ссылках

- `02 Components/04 Commands-types/00 Index.documentation.md` ссылается на `DocumentationUpdate.documentation.md` — файла нет (он переехал в `01 Core/`).
- В сборнике `awn.documentation.combined.md` пропущен один из 23 файлов.
- В `00 Index.documentation.md` (переписанной) написано «делятся на **две** группы», а в списке **три** буллета.
- Слой View декларирован, но **ни одного `*.view.md`** в проекте нет (`_Vision/` тоже пуст). Слой существует только на бумаге.

Это всё последствия активной разработки — нормально на этой стадии. Но при «обнови документацию» / «обнови реестр» это вылезает.

#### 4. Decl-only фичи

- `AWN-MEMORY: none|internal|external|hybrid` — «справочная метка, автоматикой не исполняется». Поле декоративное. Это намеренно или TODO?
- `AWN-AUTOMATIZATION: true` + `AWN-CRON: "0 9 * * *"` — есть таблица в реестре, но **нет исполнителя** (cron/n8n не подключены). Декларация есть, действия нет.

Это не баг, но стоит зафиксировать «фичи в стадии декларации vs фичи действующие».

#### 5. Четыре «индексных» сущности с пересекающимися ролями

- `README.node.md` (Workspace, в корне)
- `Index.node.md` (Space/Cluster/Book/Collection)
- `_Index.node.md` (старая конвенция, упоминается в `00 Index.documentation.md`)
- `00 Index.documentation.md` (документация компонента)

Они разные, но из имён это не очевидно. Стоит свести в одну таблицу-памятку.

### Где сейчас на шкале зрелости

| Уровень              | Описание                                          | AWN              |
| -------------------- | ------------------------------------------------- | ---------------- |
| 0. Идея              | Заметки об идее в одном файле                     | ✅                |
| 1. Концепция         | Описаны принципы и термины                        | ✅                |
| 2. **Каркас**        | Папки, шаблоны, команды, формат данных            | ✅ ← вы здесь     |
| 3. Стабильный контракт | Одна YAML-схема, валидатор, нет призраков       | ⏳                |
| 4. Тулинг            | CLI, linter, тесты сборки, CI-pipeline            | ⏳                |
| 5. Экосистема        | Шаринг шаблонов, чужие vault-ы по тем же правилам | ⏳                |

Сейчас уверенный **уровень 2** с прицелом на 3. Чтобы перейти на 3 — нужно «заморозить» YAML-схему и пройтись по проекту с этим эталоном (то самое, что подсвечено в долге №1).

### Сравнение с аналогами

В нише PKM-фреймворков ничего точно похожего не видно:

- **Tana / Capacities** мощнее «из коробки», но запирают в свой формат. AWN — обратное: plain Markdown, никакой проприетарной БД.
- **Logseq / Obsidian-only-конвенции** не формализуют **протокол с агентом**. У них агенты — внешние, у AWN — резидент vault'а.
- **OpenClaw / SOUL.md / Skill-based-системы** — у каждого свои закрытые конвенции, нет общего «контракта».
- **Andy Matuschak's Evergreen Notes / Maggie Appleton's Digital Gardens** — отсюда идея атомарности, но они не про машинный API.

AWN попадает в **редкую нишу**: «протокол человек ↔ агент с открытым контрактом». Это интересно.

### Что я бы делал дальше (в порядке убывания пользы)

1. **Заморозить одну YAML-схему**: одно из трёх (`AWN-`-UPPER-KEBAB / `awn_`-snake / `AWN-CORE-`-старая). Прописать в `04 Templates/Type.schema.md` и в `Skeleton-Node.template.md`. Прогнать все ноды через эту схему.
2. **Починить генератор `awn.documentation.combined.md`** (пропуски, пути, нумерация). Сборник — главное окно в проект, его качество = доверие к каркасу.
3. **Снести призраки** в `02 Components/04 Commands-types/00 Index.documentation.md` и `awn.registry.template.md`.
4. **Договориться с собой**: kebab-case в именах файлов — это правда или мёртвое правило?
5. **Архивировать `01_Documentation/`, `SR/`, `Test/`, `Без названия.md`, `Ttttttttttttt.md`** в `_Trash/` или `_Archive/`. Каркас должен быть стерильным; черновики — отдельно.
6. **Сделать `awn.changelog.md`** — лог изменений самой спецификации. Когда схема меняется — это должно быть видно.

### Личное впечатление

Это сделано с головой и с любовью. Видно, что вы не просто складываете заметки, а **проектируете язык** для пары «человек ↔ агент». Очень многие так не делают — они либо строят жёсткую онтологию и задыхаются, либо плывут «по течению» и теряются. У вас — третий путь: **тонкий контракт + договорённости + рост по необходимости**. Это самый трудный путь, но и самый устойчивый в долгую.

Каркас собран. Дальше — **дисциплина прополки** (синхронизировать конвенции, чистить призраки, замораживать решения). Это уже другая работа — менее творческая, более муравьиная. Но без неё каркас постепенно превращается обратно в кучу заметок.

## Шаринг шаблонов и чужие vault-ы по тем же правилам

Это про **переход от «личного проекта» к экосистеме**, где AWN живёт уже не только у вас, но и у других людей — и они могут обмениваться кусками между vault-ами, не ломая друг другу систему.

Разберу по двум составляющим: «шаринг шаблонов» и «чужие vault-ы по тем же правилам».

### Шаринг шаблонов

Сейчас в `04 Templates/` лежат скелеты (`Skeleton-Node.template.md`, `Sidecar.template.md`, `Memory.schema.md`, `Type.schema.md`, заготовка `awn.registry.template.md`). Это **внутренние** шаблоны — для вашего vault.

Шаринг шаблонов — это когда такие заготовки **публикуются и переиспользуются**.

#### Что обычно шарится

- **Шаблоны нод-папок:** «нода типа `finance.book`» с готовым `Index.node.md`, заранее настроенными подпапками (`_Inbox/`, `_Content/databases/transactions/`) и view-проекциями.
- **Шаблоны нод-частей:** готовая `daily-review.node.md` с триггерами `["рефлексия", "итоги дня"]`.
- **Skill-pack'и:** набор нод про конкретную область — «AWN-pack: личные финансы», «AWN-pack: чтение книг», «AWN-pack: ведение проекта».
- **Конфиги для интеграций:** готовая `cron.configuration.md` со списком ежедневных нод-автоматизаций.

#### Как это технически выглядит у других

- **Obsidian** — есть [Obsidian Hub](https://publish.obsidian.md/hub) с community-шаблонами. Любой человек может поделиться своим pack-ом.
- **Logseq** — marketplace плагинов и тем.
- **VSCode** — расширения через marketplace.
- **Cursor Rules / Skills** — `.cursor/rules/*.mdc` и `.claude/skills/*/SKILL.md` уже шарят: люди публикуют их в GitHub, ставят как dependency.
- **npm / pip** — самый «жёсткий» вариант: пакеты с метаданными, версиями и зависимостями.

#### Как это могло бы выглядеть для AWN

```text
awn-packs/
├── personal-finance/
│   ├── awn.pack.md            # манифест: что внутри, версии, зависимости
│   ├── finance.book/
│   │   ├── Index.node.md
│   │   ├── _Content/databases/transactions/
│   │   └── _Vision/dashboard.view.md
│   └── parts/
│       ├── add-transaction.node.md
│       └── monthly-review.node.md
└── reading-tracker/
    ├── awn.pack.md
    └── books.collection/
        └── Index.node.md
```

Команда вроде «установи pack personal-finance» — копирует структуру в ваш vault, делает merge реестра, проверяет конфликты имён.

#### Что нужно для этого

1. **Манифест пакета** — `awn.pack.md` с `AWN-PACK-NAME`, `AWN-PACK-VERSION`, `AWN-PACK-DEPENDENCIES`.
2. **Стабильный YAML-контракт** — без него pack одного автора не пройдёт валидацию у другого (это снова к долгу №1 из общей оценки).
3. **Команда `install`/`update`** — добавляется к `01 CrudNode`, `RegistryUpdate`, `DocumentationUpdate`.
4. **Конфликтные правила** — что делать, если в vault уже есть нода с таким же `AWN-ID` или путём.

### Чужие vault-ы по тем же правилам

Это про **взаимоузнаваемость** vault-ов между людьми.

#### Что это значит на практике

Я как сторонний человек/агент могу:

1. Открыть **ваш** vault (или знакомого/коллеги/клиента).
2. По наличию `awn.*` файлов в корне **сразу понять**: «о, это AWN-vault».
3. Прочитать `awn.documentation.combined.md` и `awn.registry.md` — и **за 5 минут** понять, как там всё устроено.
4. Создать ноду в вашем vault — и она **впишется** в ваши правила, потому что они зафиксированы машиночитаемо.
5. Запустить агента — и тот сразу заговорит с вашим vault-ом на одном языке.

#### Сравнение с миром кода

Когда вы открываете чужой репозиторий с `package.json`, `Cargo.toml`, `pyproject.toml`, `Dockerfile`:

- Сразу видно: это **Node-проект** / Rust-крейт / Python-пакет / контейнеризированный сервис.
- Видно зависимости.
- Видно команды (`scripts`, `targets`).
- Можно `npm install` без чтения README.

Это работает потому что **есть общая конвенция**, которую соблюдают миллионы репозиториев.

AWN претендует на то же самое для **knowledge management vault-ов**: открыл vault, увидел `awn.registry.md` + `awn.documentation.combined.md` + структура `01 Core/ 02 Components/...` — **понял, что внутри**, не читая 1483 строк README.

#### Что это даёт

- **Передача vault'а:** заказчик/коллега/наследник может работать с вашим vault'ом без обучения «как именно вы организовали папки».
- **Многоагентность:** разные агенты (Claude, GPT, Qwen, локальный Ollama) могут работать с одним и тем же vault, потому что протокол общий — а не специфичный для одного агента.
- **Аудит:** «не работает нода автоматизации отчётов» → открыл `awn.registry.md`, нашёл строку, увидел путь и триггеры — **диагноз за минуты**, как с failing-тестом в CI.

Это и есть главный аргумент, который уже сформулирован в `README.md`:

> «знакомый или заказчик говорит "не работает нода автоматизации отчётов", не нужно читать километры логов и гадать, как устроен его "сад". Достаточно открыть реестр, найти ноду, увидеть где она лежит».

То есть направление уже понятно — просто пока не реализовано как самоисполняющийся стандарт.

#### Что для этого нужно

1. **Замороженный контракт** (тот же долг №1 из общей оценки) — иначе «правила» у каждого свои.
2. **Версионирование AWN**: «vault соответствует AWN v5» → агент знает, какие поля ожидать. Сейчас в `awn.settings.md` нет даже поля `awn.version`.
3. **Минимальный starter** — один-два примерных vault-а с разной сложностью (1 нода, 5 нод, 50 нод), которые показывают «AWN-vault выглядит вот так».
4. **Bootstrap CLI/скрипт**: `awn init` → создаёт пустой vault с базовой структурой `01 Core/`, `awn.settings.md`, `awn.registry.md`. Без необходимости вручную копировать.

### Где это уже зарождается в AWN

Зачатки уже есть:

- `INSTALL.md` — инструкция, как поставить AWN в чужой vault (по сути — bootstrap-протокол).
- `Blank/` — заготовка из `.env`, `.gitignore`, `docker-compose.yml`, `HEARTBEAT.md` (это прото-pack для нового проекта).
- `01 Core/AGENTS.bootstrap.md` — точка входа для любого агента, неважно какого.
- `awn.*` файлы в корне — это уже **«машинная сигнатура»**: увидел → понял, что это AWN.

То есть направление задано. Не хватает пары шагов:

| Шаг                                       | Что нужно сделать                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1. Канонизировать корневую сигнатуру      | Список «обязательных» awn-файлов, по которым vault опознаётся как AWN                                   |
| 2. Добавить версию протокола              | `awn.settings.md` → `awn.version: "5.0.0"`                                                              |
| 3. Сделать `Blank/` правильным template-репо | Чтобы `git clone blank && cd blank` → готовый чистый AWN-vault                                       |
| 4. Запустить `awn-packs/`                 | Отдельный репо с готовыми pack-ами под типовые задачи                                                   |
| 5. Открыть документ-спецификацию          | Короткий PDF/HTML «AWN protocol v5» на 5-10 страниц — то, что любой агент или человек прочтёт за 5 минут |

### Аналогия для интуиции

| Что есть в мире кода                  | Аналог в AWN                              |
| ------------------------------------- | ----------------------------------------- |
| `package.json`                        | `awn.settings.md` + `awn.registry.md`     |
| `node_modules/`                       | `awn-packs/` (если бы был)                |
| `npm install package`                 | «установи pack reading-tracker»           |
| `.eslintrc`                           | `04 Templates/Type.schema.md`             |
| `README.md` для разработчика          | `awn.documentation.combined.md`           |
| Bootstrap-скрипт (`create-react-app`) | `INSTALL.md` (вручную) или `awn init` (в будущем) |
| Open Source community с packages      | Сообщество AWN-vault-ов и pack-ов         |

**Кратко:** «шаринг шаблонов» = pack-менеджмент для нод. «Чужие vault-ы по тем же правилам» = когда AWN — не «ваша личная система», а **общий протокол**, по которому любой vault узнаваем и проходим как любым человеком, так и любым агентом, без обучения. Сейчас примерно 30 % пути — фундамент есть, нужна канонизация и инструменты.
