**Кратко: частично вы уже это делаете сами. Внешние «Markdown-as-SQL» библиотеки в основном дублируют `storage-index`, а не решают вашу задачу целиком.**

### Что у Agent CMS уже есть (аналог MarkdownDB / mdquery)
- **`storage-index`** + `query_workspace_storage` — SQL-подобные `where` / `sort` / `fields` / `limit` по frontmatter
- **`search_workspace_hybrid`** — смысл + текст + фильтры полей
- **`link-index`** — уже на **`better-sqlite3`**
- **`fulltext-index`**, **`semantic-search`**

То есть идея «папка `.md` → индекс → запросы» у вас **уже реализована**, но под модель Page/Slot/Content, `awn-*` схему и MCP.

### Что из перечисленного может реально помочь

| Инструмент | Полезность для Agent CMS |
|---|---|
| **MarkdownDB / mdquery / MDQL / mq-db / mdtsql** | **Низкая** — второй индекс поверх первого; нет Page/Slot/MCP/write-path |
| **Dataview (Obsidian)** | **Только для человека в Obsidian**, не для сервера/агента |
| **`better-sqlite3`** | **Уже есть** — логичный следующий шаг: materialized view из `storage-index` (JOIN, GROUP BY, SUM) — это уже в ваших заметках (`rag.md`, `optimizatsiya.md`) |
| **`gray-matter` + `yaml`** | **Средняя** — ваш парсер frontmatter сейчас упрощённый; для массивов/вложенных полей (`awn-tags`, nested YAML) пригодится |
| **`remark` / `unified`** | **Средняя** — если нужны «колонки из тела» (H2-секции, wikilinks, таблицы), как у MDQL |
| **`lunr` / `minisearch` / `flexsearch`** | **Низкая-средняя** — fulltext у вас уже есть; имеет смысл только если упёрлись в скорость |
| **DuckDB** | **Точечно** — аналитика по большим выборкам (отчёты, агрегации), не как основное хранилище |

### Что **не** стоит тащить
- Заменять `.md` на «Markdown-БД» как source of truth — сломает Obsidian, git, MCP `write_*`
- Ставить MarkdownDB **рядом** с `storage-index` — два источника правды, рассинхрон

### Практичный план для Agent CMS
1. **Развивать свой `storage-index` → SQLite sync** (файлы truth, SQLite — для тяжёлых SELECT/JOIN)
2. **`gray-matter`/`yaml`** — если frontmatter станет сложнее
3. **`remark`** — если нужен SQL/DQL по **содержимому** markdown, не только YAML
4. **Bulk-update API** поверх индекса — то, чего сейчас не хватает (массовый `awn-focus` и т.п.)

**Итого:** готовые MarkdownDB/MDQL — скорее **референс по идее**, чем библиотека для интеграции. Вам полезнее **дожать свой индексный слой** (у вас он уже на 70–80% там, куда эти tools идут) + точечно `yaml`/`remark`/`sqlite`, а не подключать отдельную «Markdown SQL» экосистему.
