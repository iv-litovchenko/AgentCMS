Объясню проще: **не «подключить MarkdownDB»**, а **дорастить то, что у вас уже есть**.

---

## Как сейчас

```
.md файлы (истина)
    ↓ сканирование
.agent-cms/storage-index/index.json   ← все frontmatter всех файлов
    ↓
query_workspace_storage({ where, fields, limit })   ← упрощённый SQL
    ↓
агент читает/пишет по одной записи через write_content_property
```

**Проблемы сейчас:**
- индекс в **JSON** — нет JOIN, GROUP BY, массового UPDATE
- массовые правки — только цикл `write_*` / `batch_invoke` по 10 штук
- парсер frontmatter простой (строки, не полноценный YAML)

---

## Что я предлагаю (3 шага, не замена файлов)

### Шаг 1 — SQLite поверх storage-index (главное)

**Файлы `.md` остаются единственным источником правды.** SQLite — только производный индекс, как у вас уже сделано для ссылок (`link-index/edges.sqlite`).

```
.md файлы (истина, git, Obsidian)
    ↓ при save / rebuild
.agent-cms/catalog.sqlite   ← строка = одна запись, колонки = awn-focus, awn-name, path…
    ↓
query_workspace_storage     ← тот же MCP для агента, внутри может быть SQL
    ↓ (новое)
bulk_update_properties      ← один вызов: «всем где X → поставь awn-focus: true»
```

**Пример — массовый фокус:**
```sql
-- внутри сервера, агент этого не видит напрямую
SELECT path FROM records 
WHERE path LIKE 'zadachi-plany-i-idei/awn-storage/main/%' 
  AND awn_status = 'open'
```
→ сервер сам пишет в `.md` только нужные поля → обновляет SQLite.

Агент по-прежнему вызывает **один MCP-tool**, а не 100 `write_content_property`.

---

### Шаг 2 — нормальный YAML-парсер (мелкий, по необходимости)

Сейчас frontmatter парсится построчно (`storage-index/frontmatter.js`). Для `awn-tags: [a, b]` и вложенных полей лучше **`gray-matter` + `yaml`**.

Это не меняет архитектуру — только точнее читается индекс.

---

### Шаг 3 — remark (только если понадобится)

Если нужны запросы **по телу** markdown (заголовки H2, wikilinks в тексте) — парсить AST через `remark`.

Пока вам хватает frontmatter — **не нужно**.

---

## Чего я НЕ предлагаю

| Не делать | Почему |
|---|---|
| MarkdownDB / MDQL как основу | Дублирует ваш `storage-index`, нет Page/Slot/MCP |
| Заменить `.md` на БД | Сломает Obsidian, git, текущие `write_*` |
| Dataview на сервере | Это плагин Obsidian, не backend |

---

## Как это выглядит для агента (до / после)

**Сейчас:**
1. `query_workspace_storage` → 47 path
2. `batch_invoke(write_content_property)` × 5 раз по 10
3. долго, много round-trip

**После шага 1:**
1. `bulk_update_properties({ where: [...], set: { "awn-focus": true } })` — один вызов
2. сервер правит `.md` + синхронизирует SQLite
3. агент получает `{ updated: 47, paths: [...] }`

**Чтение** — как сейчас: `query` + `fields` + `limit`, не отдавать 1000 записей целиком.

---

## Очерёдность

1. **SQLite-sync для storage-index** — решает массовые операции и тяжёлые выборки  
2. **bulk_update MCP** — то, о чём вы спрашивали с `awn-focus`  
3. **gray-matter/yaml** — когда упёрлись в кривой парсинг массивов  
4. **remark** — только если нужен SQL по содержимому body  

---

**Итого одной фразой:** не тащить чужую «Markdown SQL» библиотеку, а **эволюционировать свой `storage-index` в SQLite-кэш + один bulk-tool**, по тому же принципу, что у вас уже работает `link-index`.

Если нужно — могу в Agent mode расписать конкретный API для `bulk_update_properties` и схему таблицы `catalog.sqlite`.
