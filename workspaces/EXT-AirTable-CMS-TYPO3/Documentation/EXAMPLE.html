Хочу поле Виджет: редактор выбирает тип блока (отзывы, карта, CTA), дальше — настройки в JSON. Как лучше заложить в схему?
Предложение структуры (черновик)
Один столбец widget_config JSON NULL + опционально widget_preset ENUM для быстрого фильтра. В adminSchema — uiType: "widget", подполя: preset, options (объект). Валидация по JSON Schema на бэкенде после сохранения. 
{
  "widget": {
    "uiType": "widget",
    "presets": ["reviews", "map", "cta"],
    "storage": { "column": "widget_config", "format": "json" }
  }
}
Зарегистрируйте тип в реестре полей → отдельный компонент формы; ядро CRUD остаётся общим.
Ок. А если позже появятся новые пресеты без миграции?
Ответ
Храните список пресетов в конфиге расширения или в таблице widget_presets; в JSON только preset_key + параметры. ИИ здесь может предложить список ключей — проверка и деплой за вами.
Нужен ещё пресет: столбиковая диаграмма. Данные потом подтяну из отчётного API (/api/reports/services-by-month), сейчас хочу только схему и превью в админке на фейковых числах.
Конфиг виджета-диаграммы (черновик)
Заведите uiType: "chart_bar" или вложенный объект в том же widget_config. Поля: engine (chartjs | echarts), dataSource (позже URL + query), previewMock — только для UI редактора (не писать в прод-ответ API). На фронте рендерите по сохранённому JSON. 
{
  "widget_preset": "chart_bar",
  "chart": {
    "engine": "echarts",
    "title": "Услуги по месяцам",
    "dataSource": { "type": "http_get", "url": "/api/reports/services-by-month" },
    "previewMock": { "labels": ["Січ","Лют","Бер"], "values": [12, 19, 14, 22, 8] }
  }
}
Превью в карточке поля (mock — без запроса к БД)
СічЛютБерКвіТра
ИИ может сгенерировать такой JSON и подсказать оси/легенду; подключение реальных данных — в коде адаптера отчёта, не в промпте с PII.
Нужно обсудить операции с записями: что закрепить для выборки, вставки, обновления и удаления — без «живого SQL» в этом чате.
CRUD как контракт (не сырые команды)
Оформите четыре операции в API/ядре: list (фильтры, сортировка, LIMIT), create (валидация по adminSchema), update (PATCH + версия для конфликтов), delete (по умолчанию soft через deleted_at, hard — отдельное право). ИИ помогает выбрать политику и сгенерировать описание OpenAPI / JSON — исполнение только через ваш код. 
{
  "records": {
    "select": "GET /api/tables/{table}/records",
    "insert": "POST …",
    "update": "PATCH …/{id}",
    "delete": "DELETE …/{id}?mode=soft|hard"
  }
}
Граница безопасности: в этот режим не передаются персональные строки из таблиц; в промпт попадают только имена таблиц/полей и черновик JSON. Кнопки «Применить к схеме» — через ревью и git, не напрямую в прод.

Только в этом HTML: галерея превью типов диаграмм — в RecordPilot на /ai-chat не переносилась (остался макет чата и превью столбиков внутри ответа ИИ выше).

Стратегия развития проекта

Аналоги, сильные стороны и практический план vNext

1) Аналоги на рынке

  • Directus / Strapi / Appsmith / ToolJet / Budibase
  • Laravel Nova / Filament / Backpack
  • Forest Admin / Retool
  • Django Admin / Rails ActiveAdmin

2) Сильные стороны текущего проекта

  • Метаданные + универсальный CRUD (не hardcode под одну сущность)
  • Зрелый набор: filter/sort/bulk/import/export/notes/categories/backup
  • Работа с разными таблицами и сценариями в одной панели
  • Глубокая проработка relation-фильтров и операторов

3) Что из этого можно сделать

  • Вынести независимое `Admin Core` (CRUD + filter/sort + relations + batch actions)
  • Оставить TYPO3 как adapter layer, а не как core
  • Поднять standalone mini-admin UI (API-first)
  • Использовать как внутренний framework для админок в проектах

4) Где главная ценность

  • Не "еще одна CMS", а универсальный backoffice-конструктор записей
  • Быстрый запуск админки для новых таблиц и сервисов
  • Сильный UX для контент- и операционных задач

5) Практические первые шаги

  • Выделить интерфейсы: `RecordRepository`, `RecordService`, `MetadataProvider`
  • Перенести 2-3 сценария из `ListController` в core-service
  • Подключить JSON endpoints: list/create/update/delete + bulk
  • Использовать этот `EXAMPLE.html` как UI-спецификацию для MVP

6) Самый реалистичный и ценный путь (детализация)

  • Вынести `Admin Core` как независимое ядро: CRUD, фильтры, сортировка, relation, batch actions, import/export pipeline.
  • Сделать `Adapter layer`: TYPO3-адаптер оставить, но добавить нейтральный HTTP/API-адаптер.
  • Построить standalone mini-admin UI на макетах из `Documentation/EXAMPLE.html` (уже хороший базис).
  • Собрать это как продукт/библиотеку: либо internal tool для ваших проектов, либо OSS "Universal Record Admin for PHP/MySQL".

7) Где самая большая ценность (детализация)

  • Не в "еще одной CMS", а в универсальном backoffice-конструкторе записей.
  • Быстро поднять админку для любой таблицы или сервиса.
  • Дать контент-команде инструменты без разработки отдельной панели.

Соглашение по именованию v1 (полная спецификация)

Схема БД, миграции, ORM-связи, метаданные админки

1) Базовые принципы

  • Одна миграция = одна задача.
  • Именование в первую очередь должно быть предсказуемым, а уже потом коротким.
  • Тип связи задается в схеме/метаданных ORM, а не кодируется в префиксах колонок.
  • Физические колонки и виртуальные/админские поля явно разделяются.

2) Именование таблиц

  • Для сущностей используем множественное число в snake_case: users, cities, orders.
  • Технические префиксы применяем только для специальных таблиц.
  • Промежуточная M:N: mm_<left>2<right> (по алфавиту), пример: mm_exchange2token.
  • Системные таблицы (опционально): sys_* только для внутреннего фреймворка.

3) Первичные ключи

  • Колонка PK по умолчанию: id.
  • Тип: unsigned bigint/int (единый выбор по проекту).
  • Если в legacy уже используется <entity>_id, оставляем как есть; не смешиваем стили в одном подсистемном контуре.

4) Обычные колонки

  • Поля сущности: name, email, login, status, description.
  • Медиа/файлы: <field>_file_id, <field>_path, <field>_url.
  • Аудит-поля: created_at, updated_at, deleted_at (если используется soft delete).

5) Внешние ключи (1:1 и M:1)

  • Формат FK: <target>_id.
  • Примеры: city_id, born_city_id, parent_id.
  • Если ссылок на одну таблицу несколько, используем ролевые имена: billing_city_id, shipping_city_id.

6) Связи один-ко-многим и многие-ко-многим

  • Синтетические счетчики 1m_* / mm_* по умолчанию не храним как физические колонки.
  • Для счетчиков используем вычисляемые запросы или материализованные кеш-поля: related_<entity>_count.
  • Для M:N используем pivot-таблицу, а не CSV в одной колонке.

7) Промежуточные таблицы (M:N)

  • Имя: mm_<a>2<b>, в алфавитном порядке.
  • Колонки: id (или составной PK), <a>_id, <b>_id, опциональные метаданные.
  • Индексы: индекс на каждый FK + уникальный составной индекс на пару, если дубликаты запрещены.

8) Правила миграций

  • Имя миграции отражает ровно одно действие: create_users_table, add_born_city_id_to_users_table.
  • Избегаем смешанных миграций (создание таблицы + несвязанные индексы).
  • Каждая миграция с FK должна явно содержать стратегию индексирования.

9) Именование ORM-связей

  • Предпочитаем семантические имена: city(), bornCity(), tokens(), children(), parent().
  • Избегаем технических префиксов вроде relatedManyToOne..., если это не требуется генератором.
  • Для framework-agnostic ядра используем канонические ключи в метаданных и внутреннее маппирование.

10) Именование метаданных админки

  • Разделяем физические (DB) и виртуальные (computed/UI-only) поля.
  • Рекомендуемые префиксы для виртуальных: virtual_... / computed_....
  • Фильтры и сортировка должны ссылаться на канонические ключи полей в метаданных.

11) Стратегия совместимости с legacy

  • Legacy-колонки типа category_id/category_name допустимы в старых модулях.
  • Новые модули должны следовать v1.
  • При миграции сохраняем стабильность имен в БД и, при необходимости, даем нормализованные алиасы через карту метаданных.

12) Пример (рекомендуемый стиль)

13) Антипаттерны (избегать)

  • Кодирование кардинальности в именах физических колонок (m1_*, 11_*, 1m_*) в новой схеме.
  • Хранение множества ID в одном текстовом поле ("1,2,3") вместо pivot-таблицы.
  • Непрозрачные универсальные префиксы для всех полей (prop_*, propref_*) без веской причины.
  • Смешивание стилей PK id и <entity>_id в одном bounded context.

14) Матрица выбора (кратко)

  • Нужно делать контентные страницы сайта? -> сначала CMS.
  • Нужна внутренняя панель для работы с данными? -> сначала Universal Admin.
  • Нужно и то и другое? -> CMS как адаптер + общий Admin Core.

Документация: три слоя описания таблиц + файл схемы

Как описывать структуру один раз и использовать везде

На основе чего описывать таблицы и структуру

  • DB-first (рекомендуется для этого проекта). Источник правды: SQL-таблицы + миграции. Поверх — отдельный слой метаданных для UI: подписи полей, типы виджетов, фильтры, связи и виджеты relation.
  • Model-first. Источник: PHP-модели, атрибуты, аннотации. Из них генерируются миграции и UI (или наоборот синхронизируются с БД).
  • Schema-first (JSON/YAML DSL). Источник: один файл схемы (например schema.yaml или *.schema.json), из которого генерируются БД, формы и API — удобно для «зелёных» проектов без legacy.

Для текущего TYPO3/наследуемого проекта оптимально: DB-first + metadata registry — потому что база уже есть и есть legacy; не нужно выдумывать схему с нуля в одном DSL, достаточно отразить факт из БД и донастроить админ-часть.

Практично: три слоя

  1. Physical schema — БД и миграции: реальные таблицы, колонки, типы, индексы, FK. Это то, что хранится в MySQL.
  2. Semantic schema — связи и доменные имена: кто с кем belongsToMany, pivot-таблицы, человекочитаемые сущности, алиасы к колонкам.
  3. Admin schema — как это рисовать в админке: какие колонки в списке, секции формы, фасеты, bulk-действия, операторы фильтров, import/export.

Тогда одна таблица описывается один раз (набором этих трёх слоёв в одном артефакте или в связанных файлах), а используется в:

  • list view (таблица, сортировка, колонки);
  • edit form (секции, виджеты, валидация);
  • filter / sort;
  • import / export (маппинг колонок, обязательные поля);
  • API (контракт ответов и действий).

Файл services.schema.idea.json

Лежит рядом с этим HTML: Documentation/services.schema.idea.json. Это не миграция и не готовый SQL — это идея-спецификация: черновик «источника правды» для генератора админки или для согласования с командой.

Как этим пользоваться

  1. Согласовать схему — править JSON как контракт: какие поля, связи, что видно в таблице.
  2. Синхронизировать с БД — по physicalSchema писать или проверять миграции; JSON не заменяет SQL, а документирует и задаёт цель.
  3. Подключить metadata registry — загрузить такой файл (или его куски) в рантайме админки или сгенерировать PHP/YAML из него.
  4. Расширять — копировать файл под новую сущность (branches.schema.idea.json) и менять блоки по шаблону.

Чего «нет» по замыслу — и это нормально

  • Не цель повторить целый CMS-сайт: дерево страниц, рендер, кеш страниц — отдельный продукт или адаптер.
  • Не цель на старте дать low-code конструктор дашбордов уровня Retool — фокус на таблицах, формах и схеме.
  • Не цель заменить CRM/тяжёлую аналитику — отчёты можно вынести в отдельные экраны или джобы.

Чеклист «чтобы не упереться» (приоритизировать по важности)

  1. Auth и права — хотя бы роли admin / editor / read-only и список доступных таблиц/операций.
  2. Audit log — кто, когда, какая сущность; опционально diff полей.
  3. File pipeline — загрузка → storage → ссылка в БД → превью в форме.
  4. Событие «запись изменилась» — webhook или очередь (инвалидация кэша сайта, поиск).
  5. Контракт API — OpenAPI или явная таблица эндпоинтов, чтобы фронт не гадал.

Итог: с аналогами мы не конкурируем «магией таблиц» — мы её проектируем. Пробелы в безопасности, файлах, поиске и фоне нужно закрывать по мере роста из «инструмента для себя» в «платформу для команды».

Идеи из Contao CMS (что полезно унести в Universal Admin)

Contao ближе к TYPO3 по духу: декларативная конфигурация таблиц (DCA), разные режимы списка, версии — без копирования всего CMS

Архитектура и конфиг

  • DCA (Data Container Array) — один PHP/JSON-описатель на таблицу: колонки, палитры кнопок, права, callbacks — очень близко к вашему adminSchema + TCA-подходу. См. Contao DCA reference.
  • Режимы контейнера — list / parent / tree: одна сущность может открываться как плоский список, как дети родителя или как дерево — у вас уже есть макеты 0.6–0.7; имеет смысл явно хранить listMode: flat|parent|tree в метаданных.
  • Глобальные vs локальные операции — в списке отдельно «действия над строкой» и «над выделенными / всей выборкой» (аналог ваших bulk + иконок в строке).

UX формы и списка (стоит позаимствовать)

  • Несколько кнопок сохранения — «Сохранить», «Сохранить и закрыть», «Сохранить и создать новый» — снижает клики при массовом вводе. Описано в ручнике Contao (редактирование записей).
  • Версионирование записей — флаг уровня таблицы (у Contao enableVersioning в config DCA): выпадашка версий + откат — укладывается в ваш блок «История» в макете 3.1.
  • Picker файлов из единого хранилища — не «голый input file», а выбор из библиотеки с превью (у вас это близко к FAL/Media полям).
  • Сортировка записей с ручным порядком — drag handle + поле sorting (как у вас SpecialSorting) — в Contao типичный паттерн для таблиц без дерева.
  • Буфер обмена (cut/copy) — «вырезать запись и вставить под другим родителем» для иерархий; можно позже как power-user фича.

Базовые сущности платформы и меню администратора (не контент сайта)

Зачем базовые таблицы

  • users — учётки входа в админку (или SSO id + профиль).
  • roles + permissions (или JSON policy на роль) — кто видит какие таблицы и операции (read/create/update/delete/bulk/import).
  • sessions / api_tokens — HTTP API и «запомнить меня».
  • audit_log — опционально, но сильно помогает в команде.
  • projects / tenants / connections — какой сайт → какая БД / префикс / ключ API (см. ниже).

Несколько сайтов и разные БД

Да, это нормальная схема: в таблице projects хранить DSN (или имя профиля подключения), кодировку, префикс таблиц. Ядро грузит adapter по активному проекту. Варианты: (A) одна БД и колонка tenant_id везде — проще бэкапы; (B) отдельная БД на клиента — жёстче изоляция, сложнее деплой. Один репозиторий кода — много конфигов подключений.

Redis, векторные БД, NoSQL

  • Redis — имеет смысл почти всегда: сессии, кэш метаданных схемы, очередь задач, rate limit API.
  • Векторная БД — не ядро CRUD; подключается, если делаете RAG/поиск по документам для агентов. Данные админки остаются в реляционной БД.
  • Другой NoSQL — опционально для логов, событий, аналитики кликов; опять же не обязателен для MVP.

Админка vs Obsidian (для тебя и для агентов)

Obsidian — сильна в связанных заметках, свободном тексте, личной структуре вроде Atlas/Focus/Forge: агентам удобно читать цельные .md, делать семантический поиск по папкам. Таблицы и Bases — удобны, но это не замена транзакционной БД с правами и API.
Эта админка — для операционных данных (услуги, заявки, пользователи сайтов, роли): предсказуемая схема, запросы, совместная работа, интеграции.
Гибрид, который имеет смысл: Obsidian = знания и процессы «как я думаю»; БД админки = то, что должно жить в проде. Для агентов: маркдаун — для контекста и правил; БД — для фактов и CRUD. Векторку имеет смысл, если индексируешь именно статьи/доки для ответов, а не вместо учётных таблиц.

Сводка обсуждения в формате Q&A (дублирует и структурирует блок выше «Макет S»)

В: Будут ли базовые модели (таблицы) — пользователи, роли, права?

О: Да, это разумный минимум самой админки-платформы, отдельно от контентных таблиц сайта: users; roles и набор permissions (или JSON-политика на роль); связь пользователь↔роль; опционально sessions, api_tokens, audit_log; плюс сущность проектов/арендаторов (projects) — какой сайт к какой БД подключён.

В: Можно ли подключать разные сайты / разные БД (БД₁ — сайт₁, БД₂ — сайт₂), а не один проект?

О: Да. В реестре хранятся профили подключения (DSN или имя конфига); ядро выбирает adapter по активному проекту (переключатель в шапке → project_id). Варианты: одна БД + колонка tenant_id везде (проще бэкапы и миграции) или отдельная БД на клиента (жёстче изоляция). Один репозиторий кода — много конфигов.

В: Имеет ли смысл подключать Redis, векторные БД, другой NoSQL?

О: Redis — да, почти всегда уместен: сессии, кэш метаданных схемы, очереди, rate limit API. Векторная БД — не замена реляционной админке; рядом, если нужен RAG/поиск по документам для агентов. Учётные данные и CRUD остаются в SQL. Другой NoSQL — опционально для логов/событий; для MVP не обязателен.

В: Будет ли меню настроек? Какие пункты?

О: Да — системное меню не путаем с контентом сайта. Визуальный макет: секция «Макет S» выше: группы Площадка (проекты и БД, окружения, квоты), Доступ (пользователи, роли, API-ключи, аудит), Интеграции (webhooks, очереди/cron, почта), Инфра (Redis, поиск, файлы, опционально вектор), Система (логи, экспорт настроек, о программе).

В: Может ли эта админка быть «лучше Obsidian»? Где таблицы и базы в Obsidian?

О: Это разные инструменты. Obsidian — граф знаний: папки вроде Aya.AI, Atlas, Focus, Forge, Lab, Life, Inbox/Vault/Archive удобны для заметок, связей и личного процесса; агентам часто проще читать цельные .md и правила. Таблицы/Bases в Obsidian не дают полноценных транзакций, ACL и API как у прод-БД. Админка — для операционных данных в проде. Оптимально: гибрид — Obsidian для мышления и документации, БД админки для фактов, ролей и интеграций; векторный индекс — для текстов/статей, а не вместо учётных таблиц.

В: Агентам удобнее БД или обычные markdown-файлы?

О: Markdown — для нарратива, инструкций, структуры знаний (как ваш vault). БД — для структурированных записей, запросов, целостности и совместной работы. Оба формата можно использовать параллельно; выбирать по типу данных, а не «одно вместо другого».

Реализация: DB row lock / поле edit_lock_by + edit_lock_until / или WebSocket heartbeat; при сохранении — проверка version (optimistic lock), иначе конфликт «данные устарели». Для UX: не серый экран, один понятный баннер и возможность остаться в read-only.

К карте документа

Что мы ещё почти не разбирали (примеры)

  • Безопасность и комплаенс: SSO/OIDC, 2FA, политики PII/GDPR, ретеншн логов.
  • Наблюдаемость: трассировки, алерты, SLO по API админки.
  • Нагрузка и масштаб: шардирование, read-replicas для отчётов, очереди и идемпотентность.
  • Качество данных: дедуп на уровне пайплайна, «золотая запись», словари нормализации.
  • Песочница кода: пользовательские хуки только в ограниченном DSL (без eval).
  • Мобильное / офлайн: что обязано работать с телефона у полевых редакторов.

Это не «дыры в идее», а следующий слой — когда решите выводить админку из «идеального макета» в эксплуатацию.

Аналоги на рынке (обзор продуктов)

Сводка для сравнения RecordPilot / Universal Admin с готовыми решениями. Названия — ориентиры, не реклама.

К карте документа

Админка над своей БД / API

  • Directus — SQL-база, отражение схемы, REST/GraphQL; близко к идее «панель записей» поверх реальной БД.
  • NocoDB, Baserow — сетка как в Airtable поверх подключённой БД.
  • Supabase Studio — таблицы, SQL, auth; в связке с BaaS, не только «чистая» админка.

Headless CMS с админкой

  • Strapi, Payload, Keystone — модели контента и API; упор на контент, не на произвольный legacy-SQL «как есть».

Low-code панели к данным

  • Retool, Appsmith, ToolJet, Budibase — экраны, формы, запросы к БД/API; больше конструктор приложений, чем один выровненный универсальный CRUD.

Админка в экосистеме PHP / фреймворков

  • Laravel Nova, Filament, Backpack — быстрый CRUD по моделям Laravel; привязка к стеку.

Облачные / классические админки к БД

  • Forest Admin — подключение БД и готовый CRUD-слой (hosted-модель).
  • В enterprise часто встречаются Django Admin, Rails ActiveAdmin и аналоги «встроенной» админки кORM.

Чем замысел RecordPilot всё равно может отличаться

Один core + адаптеры (в т.ч. TYPO3 и не только), свой UX из этого файла, метаданные отдельно от «тела» CMS, мультипроект / мульти-БД в одной оболочке — у готовых продуктов набор не всегда совпадает один в один, но рынок «админка к данным» уже большой: вы не в вакууме.

Терминология v1: Синглтон / Коллекция / Коллекции-хранилища

Фиксация терминов для UI, схемы и документации проекта.

К карте документа

Базовые определения

  • Синглтон — одиночная запись (ровно одна запись на проект/сайт).
  • Коллекция — сущность, в которой есть много записей одного типа.
  • Коллекции — уровень группировки коллекций по «хранилищам»/доменам.

Примеры синглтонов

site_settings, homepage_seo, contacts_block, branding. Для каждой singleton-сущности в интерфейсе обычно нет длинного списка строк; сразу открывается форма одной записи.

Примеры коллекций (много записей)

services, articles, faq, branches, clients. Для коллекций доступен список (grid/table), фильтры, сортировка, bulk-действия и переход в форму конкретной записи.

Коллекции как «хранилища» (группы)

  • Контент
  • Каталог
  • CRM
  • Система
  • Медиа

Это навигационный уровень: внутри каждого «хранилища» лежат конкретные singleton/collection сущности.

Пример иерархии

  • Контент (хранилище) → homepage_seo (singleton), articles (collection), faq (collection).
  • Каталог (хранилище) → services (collection), service_page_settings (singleton).
