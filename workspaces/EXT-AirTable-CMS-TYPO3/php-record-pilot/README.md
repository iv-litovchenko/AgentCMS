# RecordPilot — требования к архитектуре (PHP)

Черновик для реализации **универсальной панели записей** (CRUD + метаданные + адаптеры к БД), в духе спецификации в `Documentation/EXAMPLE.html` и `Documentation/services.schema.idea.json`.

**Цель документа:** зафиксировать **границы слоёв**, **паттерны** и **правила зависимостей**, чтобы ядро оставалось переносимым (TYPO3 как один из адаптеров, не как «центр вселенной»).

---

## Приоритет автора: с чего начать (первый заход)

Так автор видит **порядок работ** до остальных списков:

1. **Форма авторизации** — вход в панель (логин/пароль или иной минимальный способ).
2. **Главная страница** — после входа: обзор / точка входа в разделы панели.
3. **Страница настроек площадки** — конфигурация самой панели (подключения, роли, глобальные параметры).

### Супер-администратор

- Заводим **одного супер-администратора**, у которого есть доступ **ко всей панели** и **ко всем БД/площадкам**, которые перечислены в системе.
- Права супер-админа и список подключений к БД задаются в **`config/panel.php`** (экран `/settings` показывает их; редактирование из UI — позже).
- **Реализовано в коде:** `/login` → `/` (главная по логотипу, заготовка выбора БД) → **`/dashboard`** (пункт меню «Главная»: виджеты и обзор) → `/settings`; сессия; один супер-админ = доступ ко всем перечисленным подключениям (CRUD пока использует `connection_id` из `config/vertical_slice.php`, по умолчанию `default`).

Ниже — **общий продуктовый список** (§0), старые стратегические пункты (§0.1) и **техническая часть**.

## 0. С чего начинаем по продукту (10 пунктов)

Сначала — **простое и проверяемое руками**, без больших концепций. Сложное из макетов — **после** того, как «список → открыть → сохранить» уже работает.

1. **Одна сущность на старте** — выбрать одну таблицу/тип записи (например услуги) и не расползаться на весь справочник сразу.
2. **Минимальный сценарий** — **список → открыть запись → поменять поле → сохранить**; пока этого достаточно.
3. **Опираться на готовый пример схемы** — взять за образец `services.schema.idea.json` / кусок из `EXAMPLE.html`, не придумывать новый формат «с нуля» в первый день.
4. **Одна база, один «проект»** — переключатели проектов и разные БД можно **не трогать**, пока не устаканится один рабочий поток.
5. **Макеты как ориентир, не как чеклист** — `EXAMPLE.html` — источник идей; **не** пытаться повторить все экраны подряд.
6. **Завести короткий backlog** — выписать 3–5 фич из макетов «на потом» (импорт, webhooks, блокировки и т.д.), чтобы не забыть, но **не** делать их в первой итерации.
7. **Понятные слова в меню** — как назвать разделы (синглтон/коллекция или проще) можно **уточнить позже**; главное — не ломать URL, когда решите.
8. **Заметка редактора** — отдельное поле «что сделали с записью» (как UserWorkNote) — **удобно**, но не обязательно в самом первом прототипе.
9. **Позиционирование одной фразой** — зафиксировать для себя/команды: «это панель к **данным**, не замена TYPO3-страницам» — чтобы не путать цели; без длинных презентаций.
10. **Сознательно потом** — схема БД как картинка, ИИ по метаданным, SSO/комплаенс, «большая безопасность» — из обсуждений и конца `EXAMPLE.html`; к ним возвращаемся, когда пункты 1–2 уже стабильны.

**Идея:** первые шаги = **узкий кусок реальной работы редактора**; всё остальное — нарастает слоями.

### 0.1 Предыдущие 10 пунктов (стратегические ориентиры)

Это тот более «широкий» список, который был раньше, сохранён как ориентир следующего уровня.

1. **Позиционирование** — зафиксировать формулировку: **панель записей / backoffice к данным**, а не «ещё одна CMS»; сайт рендерит фронт, RecordPilot управляет **записями и схемой** в привязке к проекту/БД.
2. **Мультипроект / мульти-БД** — в шапке осмысленный переключатель «проект -> своё подключение» (как в макете обзора), даже если в коде сначала один проект.
3. **Терминология в интерфейсе** — **синглтон** (одна запись), **коллекция** (много записей), **хранилища** (группы сущностей); навигация и URL должны это не ломать.
4. **Один вертикальный срез end-to-end** — одна сущность: **список -> карточка/форма -> сохранение**, с метаданными из `*.schema.idea.json`, без расползания на все таблицы сразу.
5. **Метаданные как контракт** — один эталонный файл схемы (как `services.schema.idea.json`): физика БД + `adminSchema` для списка и формы; ИИ и генераторы опираются на него, а не на «устные договорённости».
6. **Поле «работа редактора»** — отдельное пользовательское поле (аналог **UserWorkNote**): что делали с записью, без смешивания с публичным контентом.
7. **ИИ только по структуре** — отдельный сценарий: обсуждение полей, связей, CRUD-контрактов **без выдачи строк прод-БД** в чат (как в `IDEA_AI_SCHEMA_COLLABORATION.md` и макете схема-чат).
8. **Визуальная карта данных** — запланировать экраны **схемы БД** (ER / матрица / граф) как следующий крупный шаг после стабильного CRUD — из макетов 13.x в `EXAMPLE.html`.
9. **Backlog идей из макетов** — не делать всё сразу: завести приоритетный список из **EXAMPLE** (блокировка записи, dry-run импорта, webhooks, сохранённые виды, feature flags и т.д.) и подключать по мере необходимости.
10. **«Следующий слой» после макетов** — осознанно отложить: усиленная **безопасность** (SSO, 2FA), **наблюдаемость** (SLO, трассировки), **комплаенс** (PII, ретеншн логов) — см. блок в конце `EXAMPLE.html`, не блокируя первый рабочий прототип.

## 1. Принципы

1. **Ядро не знает про CMS** — только про «проект», «подключение к данным», «сущность», «запись», «метаданные».
2. **Источник данных — через адаптер** (MySQL/TYPO3/HTTP API позже). Ядро не строит SQL «везде напрямую» из контроллеров.
3. **Метаданные отделены от физической схемы** — физика в БД/миграциях; семантика и UI — в registry (JSON/YAML/PHP-конфиг).
4. **Расширяемость через реестры** — типы полей, источники данных, bulk-действия, экспорт/импорт.
5. **Безопасность по умолчанию** — ACL на уровне операций и сущностей, CSRF для форм, подготовленные запросы.
6. **Тестируемость** — домен и сервисы без HTTP; адаптеры — за интерфейсами, с интеграционными тестами по желанию.

### 1.1 Принципы и практики разработки (SOLID + DRY и др.)

- **SOLID** — базовый набор правил для проектирования классов и зависимостей:
  - `S` (Single Responsibility): один класс = одна причина для изменения.
  - `O` (Open/Closed): расширяем через реестры/стратегии, а не правкой ядра.
  - `L` (Liskov): реализация адаптера взаимозаменяема без поломки сервиса.
  - `I` (Interface Segregation): узкие интерфейсы вместо «бог-интерфейса».
  - `D` (Dependency Inversion): зависим от абстракций (портов), не от PDO/HTTP деталей.
- **DRY (Don't Repeat Yourself)** — общие правила фильтров/валидации/рендера полей живут в одном месте (registry/strategy), а не копируются по контроллерам.
- **KISS** — минимальный рабочий дизайн без раннего усложнения.
- **YAGNI** — не строим «впрок» подсистемы, пока нет реального сценария.
- **Separation of Concerns** — строгие границы слоёв (HTTP, Application, Domain, Infrastructure, Metadata).
- **Explicit over implicit** — явные конфиги, явные контракты DTO, явные ошибки.
- **Fail-safe defaults** — безопасное поведение по умолчанию: deny-by-default для ACL, валидация входа до операций записи.

## 2. Слои (рекомендуемая структура)

```
php-record-pilot/
├── bootstrap/              # Минимальный PSR-4 autoload (если нет composer vendor)
├── public/                 # Точка входа, статика (css/js/images)
│   └── css/panel.css       # Стили как в Documentation/EXAMPLE.html (токены --accent, .vision-app, таблицы, кнопки)
├── config/                 # Окружение, подключения БД, маршруты
├── metadata/               # *.schema.idea.json для сущностей
├── sql/                    # Пример DDL для локальной БД
├── src/
│   ├── Http/               # Request/Response, контроллеры, middleware
│   ├── Application/        # Сценарии use-case: RecordService, ImportService
│   ├── Domain/             # Сущности, политики, исключения (без фреймворка)
│   ├── Infrastructure/     # PDO, реализации адаптеров, файловое хранилище логов
│   └── Metadata/           # Загрузка и валидация schema.idea.json, registry
├── views/                  # PHP-шаблоны (или .phtml)
├── storage/                # Кэш, логи (не в git)
└── tests/
```

Поток **типичного запроса**:  
`Http (Controller)` → `Application (Service)` → `Domain (правила)` → `Infrastructure (Adapter/Repository)` → БД/API.

**Запрещено:** вызывать PDO из шаблона; вызывать TYPO3 API из `views/`.

## 3. Границы ответственности

| Слой | Ответственность |
|------|-----------------|
| **Http** | Маршрутизация, HTTP-коды, сессия, CSRF, выбор проекта из контекста |
| **Application** | Оркестрация: list/create/update/delete/bulk, импорт, валидация входа |
| **Domain** | Инварианты: «singleton — одна запись», типы операций, доменные ошибки |
| **Infrastructure** | Конкретные драйверы: `PdoConnection`, `Typo3Adapter` (если нужен) |
| **Metadata** | Парсинг схемы, merge defaults, описание list/form/filter |

## 4. Паттерны, которые используем

### 4.1 Adapter (адаптер источника данных)

**Зачем:** подключать разные бэкенды (MySQL напрямую, TYPO3 DBAL, внешний REST).

- Интерфейс вида `DataSourceAdapter` / `ConnectionAdapter`:
  - выполнение запросов к списку записей с фильтром/сортировкой/pagination;
  - чтение/запись одной записи по ключу;
  - опционально: транзакции.

**Правило:** контроллеры и сервисы зависят от **интерфейса**, не от PDO.

### 4.2 Repository (репозиторий записей)

**Зачем:** инкапсулировать SQL/квери под конкретную сущность (`tx_services`, …).

- `RecordRepository` получает **имя сущности** + **метаданные** и строит запросы согласно `physicalSchema` / mapping.
- Для сложных join — отдельные query-объекты или read-model, не «простыня» в контроллере.

### 4.3 Application Service (сервис приложения)

**Зачем:** один вход для сценария «список записей», «сохранить», «массовое удаление».

- `RecordApplicationService::list()`, `update()`, …
- Внутри: проверка прав, валидация DTO, вызов репозитория, доменные события (опционально).

### 4.4 DTO / Input objects

**Зачем:** явные структуры входа (фильтры, поля формы), без «магии» `$_POST` по всему коду.

### 4.5 Strategy (стратегии)

Где уместно:

- **Типы полей** (FieldType): `TextField`, `RelationField`, `JsonField` — рендер виджета, правила валидации, нормализация перед сохранением.
- **Операторы фильтра** (`=`, `LIKE`, `IN`, диапазон дат).
- **Экспорт** (CSV/XLSX) — отдельные стратегии.

### 4.6 Factory / Registry (фабрики и реестры)

- **FieldTypeRegistry** — регистрация типов полей из `adminSchema`.
- **BulkActionRegistry** — действия «с отмеченными…».
- **MetadataProvider** — загрузка и кэш `schema.idea.json` по сущности/проекту.

### 4.7 Middleware / Pipeline (для HTTP-слоя)

Цепочка: `Auth` → `ProjectContext` → `Csrf` → `Controller`.

На чистом PHP — простые callable или классы с методом `handle($request, $next)`.

### 4.8 Optional: Domain Events / Hooks

- События `RecordSaved`, `RecordDeleted` — для webhooks, инвалидации кэша, поиска.
- Пользовательские хуки — только через **ограниченный DSL** или конфиг (без `eval`).  
  (См. обсуждение «песочница» в `EXAMPLE.html`.)

## 5. Метаданные и конфигурация

- Файлы вида `*.schema.idea.json` — **контракт** для UI/генерации форм (не замена SQL-миграций).
- В рантайме: **merge** defaults + валидация схемы (обязательные поля, типы виджетов).
- Версионирование: `meta.version` в JSON.

## 6. Терминология предметной области (из документации)

- **Синглтон** — одна запись на проект/сайт.
- **Коллекция** — много однотипных записей.
- **Коллекции (хранилища)** — группировка сущностей по доменам (Контент, Каталог, …).

Отображение в URL/UI:  
`/project/{id}/vault/{vaultId}/entity/{entityKey}` → list → `/record/{id}`.

(Точные пути — на этапе проектирования роутинга.)

## 7. Безопасность (минимум)

- Подготовленные запросы (PDO prepared statements).
- RBAC: роль → список сущностей и операций (`read`, `create`, `update`, `delete`, `bulk`, `export`).
- CSRF-токены для всех форм, меняющих состояние.
- Логирование аудита: кто, когда, какая сущность, какой id (опционально diff полей).

## 12. Запуск и проверка (локально)

1. Создайте БД и примените [sql/schema.sql](sql/schema.sql) (таблица `services` + тестовая строка).
2. Подключение к MySQL задаётся в [config/database.php](config/database.php) (по умолчанию `127.0.0.1:3306`, БД `recordpilot`). Способы:
   - **Переменные окружения:** `DB_DSN`, `DB_USER`, `DB_PASSWORD` (имеют приоритет над значениями по умолчанию).
   - **Локальный файл (удобно для Docker):** скопируйте [config/database.local.example.php](config/database.local.example.php) → `config/database.local.php` и укажите свой `dsn` / `user` / `password`. Файл `database.local.php` в [.gitignore](.gitignore).

### 12.1 Ошибка `SQLSTATE[HY000] [2002] Connection refused`

Это значит: **на хосте и порту из DSN никто не слушает** (MySQL не запущен, другой порт, или неверный host).

| Ситуация | Что сделать |
|----------|-------------|
| MySQL не стартовала | Запустите службу MySQL/MariaDB локально или контейнер с БД. |
| `php -S` на хосте, MySQL в Docker | Пробросьте порт `3306:3306` в контейнер и оставьте в DSN `host=127.0.0.1` (или `localhost`). |
| PHP в Docker, MySQL в другом контейнере | В DSN укажите **имя сервиса** из `docker-compose` (например `mysql` или `db`), **не** `127.0.0.1`. |
| PHP в Docker, MySQL на машине-хосте | На Mac/Windows в DSN часто используют `host=host.docker.internal`. |

Проверка с той же машины, где крутится PHP:  
`mysql -h127.0.0.1 -P3306 -uroot -p -e "SELECT 1"` (подставьте host/port/user из вашего DSN).

4. Дополнительно: для среза CRUD — `VERTICAL_SLICE_CONNECTION_ID`; отображаемое имя площадки — `PLATFORM_DISPLAY_NAME`. См. [config/app.php](config/app.php).
5. **Вход в панель:** в [config/panel.php](config/panel.php) по умолчанию логин **`admin`**, пароль **`changeme`**. Для продакшена задайте `PANEL_SUPER_ADMIN_USER` и `PANEL_SUPER_ADMIN_PASSWORD_HASH` (получить хэш: `php -r "echo password_hash('ВАШ_ПАРОЛЬ', PASSWORD_DEFAULT), PHP_EOL;"`).
6. Автозагрузка: либо `composer dump-autoload`, либо [bootstrap/autoload.php](bootstrap/autoload.php) (подключается из `public/index.php`, если нет `vendor/autoload.php`).
7. Встроенный сервер PHP: `php -S localhost:8080 -t public` из каталога `php-record-pilot/`.
8. Проверка: `GET /health` (без авторизации) → откройте `/` → редирект на `/login` → войдите → **`/`** (главная, выбор БД — заготовка) → **`/dashboard`** (меню «Главная») → **`/settings`** (меню пользователя в шапке) → `/records/services` → **`/migrations`** → **`/export`** / **`/import`** → **`/files`** (заготовка просмотра файлов по FTP) → **`/check`** (раздел «Проверки» — заготовка) → **`/ai-chat`** (макет «Чат с ИИ» из EXAMPLE) → **`/docs`** → **`/docs/mockups`** (карта макетов из EXAMPLE.html).
