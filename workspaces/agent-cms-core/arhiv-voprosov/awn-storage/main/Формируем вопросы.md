> Архив — исходные Q&A до SPEC.

Никто пока не делает именно «все MD-файлы живут по одним принципам подгрузки + типы строго из пути + схемы рядом с папками для переносимости + structured-data слоты где угодно». Это довольно свежая и чистая комбинация.

Вот практичный пример структуры папок, который полностью соответствует твоей идее:

- типы определяются путём
- схемы лежат рядом с папками (переносимость)
- инфоблоки можно создавать не только в awn-data, но и внутри тем
- дерево страниц живёт отдельно
- записи — обычные .md
- override возможен на уровнях Core → WS → Area → Раздел

### Q1. Как определять тип (пространство имен)?

**✨  Файл = Сущность (каждый .md это запись, каждая папка с _infoblock.yaml это инфоблок)** Главная мысль: **все `.md`-файлы должны быть одной природой**, но у них может быть разная роль: просто текст, схема/тип, инфоблок-накопитель, запись, страница, слот, override и т.д.  **Файл/папка = узел (node).**  
Если у него нет `awn-*`-свойств — это обычный markdown-документ.  
Если есть `awn-*`-свойства — это уже типизированный объект системы. - **Объект без свойств** = просто обычный md-файл (не инфоблок и не запись).



Лучше через путь пакетов/папок (как в Neos): awn.core.editing-fields.fields.string или ws.myproject.news.collection. - **Объект без свойств** = просто обычный md-файл (не инфоблок и не запись).

$$\text{Type ID} = \langle Vendor/Agent\rangle.\langle Domain/Module\rangle.\langle EntityType\rangle$$
```
Формат: <kind>:<type>:<role>
data-source: ws/main/data/course-1
<vendor>.<domain>.<entity>
<package>.<module>.<type>
```

$$\text{Сущность} = \underbrace{\text{Kind}}_{\text{Функция}} + \underbrace{\text{Type}}_{\text{Форма}} + \underbrace{\text{Role}}_{\text{Смысл}}$$

| **Kind (Как работать)** | **Type (Какая структура)** | **Role (Что внутри)** | **Что это в реальности?**                      |
| ----------------------- | -------------------------- | --------------------- | ---------------------------------------------- |
| `container`             | `collection`               | `news`                | Инфоблок «Новости» (список новостей)           |
| `container`             | `single`                   | `news`                | Настройки модуля «Новости» (1 файл с конфигом) |
| `row`                   | `item`                     | `news`                | Одна конкретная новость (статья)               |
| `container`             | `collection`               | `tasks`               | Канбан-доска / Инфоблок «Задачи»               |
| `row`                   | `item`                     | `tasks`               | Одна конкретная задача                         |
Вариант 4: **Class → Type → Subtype** (самый ООП-шный)
АЛЬТЕРНАТИВА (если хочешь совсем просто)  Можно объединить в одно поле: # Вместо трех полей - одно составное awn-type: container.infoblock.collection
Вообще мне кажется, **Kind + Type + Role** — это слишком сложно. Через полгода ты сам забудешь, что куда писать.

### Q2. Нужно ли явно указывать `awn-id`?

**Нет.** Сохранение `awn-id` внутри frontmatter создает конфликты при дублировании файлов.
- `awn-id` = путь от корня проекта (например, `news/2024/hello-world`)
- Не хранится в файле, вычисляется автоматически
### Q3. Нужен ли глобальный реестр типов (Global Registry)?

**Да, но гибридный.**
Да, нужен. Минимум один индексный файл на уровне WS + возможность локальных деклараций. Система должна знать, чем она оперирует.

- **Core Registry:** Базовые типы ядра (`awn.base.*`) вшиты в систему.
- **Auto-Discovery:** При загрузке Workspace система сканирует все файлы `awn-kind: container` и регистрирует найденные `awn-role` / `awn-schema` в единый runtime-реестр типов.

### Q5. Схема переопределения (Override Chain)
```flowchart LR

  A[Файл .md] --> B[Есть frontmatter?]
  B -- нет --> C[Обычный markdown-документ]
  B -- есть --> D[Есть awn-* поля?]
  D -- нет --> C
  D -- есть --> E[Определяем awn-kind]
  E --> F[schema / container / item / mixin / mount]
  F --> G[Определяем тип из манифеста/пути]
  G --> H[Загружаем схему типа]
  H --> I[Применяем override-слои]
  I --> J[Собираем runtime-объект]
  J --> K[Индекс / дерево / форма / рендер]

```

**✨  **Наследование через структуру** (kind/type/role, а не extends)
**✨  **Оверрайды по пути** (можно менять схему на любом уровне)
**✨  ** **Декларативная типизация** (все схемы в YAML, а не в коде)
**✨  **Портативность** (папку можно скопировать — она самодостаточна)

По дереву: Core → WS → Area → Раздел → Конкретный инфоблок. Префиксы awn-core-*, awn-ws-*, awn-x-* — отличная идея.

Переопределение схем работает по принципу всплытия/погружения по дереву каталогов:

$$\text{Effective Schema} = \text{Core Schema} \leftarrow \text{WS Config} \leftarrow \text{Area Config} \leftarrow \text{Local Container (.md)}$$

Каждый дочерний уровень может переопределять свойства родителя через префиксы каскадирования:

- `awn-core-*` — свойства ядра (нельзя переопределить).
- `awn-ws-*` — установки уровня Workspace.
- `awn-x-*` / `attr_*` — свободные пользовательские атрибуты.

core
  -> ws
    -> area
      -> category
        -> local node (итоговая схема объекта)

awn-core-*     — базовые поля и поведения ядра
awn-ws-*       — поля/схемы конкретного workspace
awn-area-*     — уровень области/зоны
awn-section-*  — уровень раздела
awn-x-*        — произвольные пользовательские поля

### Q6. Произвольные (уникальные) свойства записи (`attr_*`)

Для хранения гибких данных без предварительного жесткого описания схемы используйте префикс **`attr_`** (или вложенный блок `attributes:`). Это изолирует системные свойства `awn-*` от пользовательских данных:

- Да, attr_* или один JSON-блок awn-attributes. Уникальные комбинации — нормально.

```
Системные метаданные
awn-kind: row
awn-type: awn.page.topic

Динамический JSON-like набор атрибутов
attributes:
  custom_score: 98.5
  payload:
    gate_id: 12
    tags: ["fast", "cron"]
```
### Q7. Где хранить схемы: Один файл или разрозненно по папкам?

Размазанный — обязательно. Если всё в одном корневом файле — перенос папки убивает систему. Лучше: схема рядом с папкой + возможность наследования/override.

**Распределенный подход (Co-location) — единственно верный для локального DX.**

- **Проблема монолитного файла:** Потеря портативности. Нельзя просто скопировать папку `/news` в другой Workspace.
- **Решение:** Файл `_schema.md` (или файл самого контейнера) лежит **внутри папки** с элементами.
- При переносе папки переносится и схема инфоблока, и все его записи.

### Q8 Общий реестр типов (domains)

Общий реестр типов (domains) Да, нужен. Минимум один индексный файл на уровне WS + возможность локальных деклараций. Система должна знать, чем она оперирует.

/.awn/registry.json

```
{
  "types": {
    "acme.news.record": {
      "path": "/ws/main/data/news/_schema.record.md",
      "package": "acme.news",
      "kind": "schema"
    },
    "acme.news.infoblock": {
      "path": "/ws/main/data/news/_container.md",
      "package": "acme.news",
      "kind": "container"
    }
  }
}

```
### Q9. Инфоблоки внутри слотов (Структурированные данные прямо в Темах)
