Memory CMS: замечания после теста MCP

Замечания из живого теста коннектора Memory CMS на maptex.ru, октябрь 2026.

## Срочно

1. ==✅== Файл .env попал в публичный репозиторий. Если там настоящие пароли и токены, их нужно сменить, а сам файл удалить из истории git (через git filter-repo или BFG), добавить в .gitignore и хранить вместо него .env.example. *Для нас: в git только схема; живые ключи пользователь задаёт сам — не критично, держим `.gitignore`.*
2. ==✅== Данные лежат в volume Докера, а не в обычной папке. Сначала сделать копию, потом переделать на bind mount вроде ./workspaces:/app/workspaces. Не запускать docker compose down -v. *В актуальном коде уже bind `./workspaces`; пункт про legacy VPS (maptex), не дефект репо.*
3. ==✅== Git не включён, резервных копий нет. *Git опционально (MCP `module_git_*`); снимок данных — **`agent-cms-cli backup`** / **`restore`**.*

## Система и MCP

1. В корне хранилища нельзя создать или удалить файл через MCP: content_create и delete_content не работают для placement.kind=root.
2. SVG не записывается через content_write: система считает его бинарным, а не текстом.
3. У topic_create в описании инструмента пустой список параметров, название пришлось угадывать.
4. При database_register описание не сохраняется, вместо него встаёт название инфоблока.
5. В каждом новом инфоблоке сама появляется лишняя «Первая запись».
6. record_url_get возвращает внутренний адрес Докера http://cms:3000/..., а не публичный maptex.ru.
7. database_register возвращает всю схему, около 40 полей с переводами, и съедает много токенов.
8. Загрузка файлов через base64: маленькие файлы проходят, большие фото ломаются. По словам автора, уже переделано, нужно перепроверить.

## Сервер и хранилища

1. Три мёртвых хранилища (ws-focus, ws-medcenter, Downloads) ссылаются на папки с макбука, а ws-medcenter стоит хранилищем по умолчанию.
2. В корне шести новых хранилищ остались старые preview.svg, их нужно удалить вручную.
3. В описании 0-ws-test опечатка: «Описчание».

## Скорость и токены

Запросы отрабатывали быстро, тормозили только тяжёлые ответы. Точное время каждого запроса стоит смотреть в логах сервера.

1. Короткие ответы по умолчанию. При создании инфоблока возвращать только ID и «готово», полную схему отдавать отдельным запросом.
2. Пагинация. Списки отдавать порциями, например по 20 элементов, а не все сразу.
3. Карта хранилища на старте. Один лёгкий запрос, после которого агент знает, что где лежит, и не делает лишних вызовов вслепую.
