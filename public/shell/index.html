Roadmap · дословно

Исходная идея (замена Aya)

Agent Shell — тонкая оболочка: слышит, показывает, говорит. Не думает — думает агент (QwenPaw, OpenClaw, Cursor…) через MCP → Agent CMS. 

Пользователь → Shell → CMS (thread/inbox или QwenPaw API)
                         ↑
                    MCP-агент

Трёхфазный план из первого обсуждения

  • Фаза 1. Shell v0 — компактное окно, SSE, статус, отправка в thread — ✅ сделано
  • Фаза 2. Голос — sidecar STT/TTS, режимы как в Aya (PTT, always, disabled) — ⚠️ частично
  • Фаза 3. Multi-agent — runtime registry, «кто отвечает», routing по теме/группе — ❌ не делали

Что обсуждали, но ещё не в footer

Архитектура Shell как «device runtime»

Shell должен знать, кто он и что умеет, а агент видит команды через один MCP (CMS):

  • agent-shell/manifest.yaml + GET /api/shell/capabilities
  • Shell регистрируется в CMS при старте (online + capabilities)
  • MCP tools: shell_screenshot, shell_clipboard_read/write, shell_record_screen, shell_window_minimize…
  • CMS проксирует команду → Shell выполняет → результат в thread

Сейчас только 3 shell-tools в MCP: shell_get_status, shell_post_message, shell_stop_tts.

Отдельное приложение

  • Agent Shell.app со своей иконкой, независимо от CMS — ✅ (agent-shell-desktop, npm run shell:dist)
  • Запуск CMS или Shell или оба — ✅
  • Shell-app потом: screenshot/clipboard через ipcMain — ❌

dashboard_nebula.html · дословно

Идея в двух словах

Это не главный интерфейс Aya (им остаётся Aya Bar — Tkinter). Nebula Dashboard — отдельная «консоль наблюдения»: красивая web-страница, которая смотрит на голосовой процесс издалека и показывает, что происходит прямо сейчас.

Запуск:

cd core/integration
./serve_dashboard.sh   # → http://localhost:8844/dashboard_nebula.html

Страница опрашивает каждые 500 ms два файла из integration/:

  • voice_status.txt — строка 1: emoji-состояние (🔴 слушаю, 🔊 говорю…), строка 2: фраза + vol= / thr=, строка 3: время
  • phrase_history.json — последние распознанные фразы
aya_voice_v2 → voice_status.txt + phrase_history.json
                        ↓ fetch 500ms
              dashboard_nebula.html
aya_bar_v2 тоже читает те же файлы

Bar — управление и компактный UI. Dashboard — большой экран «как в космическом корабле»: gauge, история, сырой дамп.

Что на странице (по смыслу)

1. Preview — визуальный монитор

  • Input level — круговой gauge по vol/thr (уровень микрофона vs порог)
  • Scene — декоративные полоски «активности»
  • Pulse — сердечко (как у бара, но в web)

2. Code — отладка — сырой текст voice_status.txt

3. History — список из phrase_history.json (до 12 строк)

4. Правая колонка Status — состояние, фраза, время обновления

5. Низ — pill Live / Listening / Speaking / Idle; кольцо «батареи» (navigator.getBattery)

6. Что только «нарисовано» (не работает)

  • Поле «Describe what you want to build…» — ни куда не подключено, заготовка
  • Левое меню (File, Assets, Voice Console…) — декоративная навигация

Dashboard — 50% живой мониторинг + 50% UI-макет под расширение.

Зачем это было в Aya

  • Видеть, жив ли голос — Bar маленький; dashboard — на втором мониторе
  • Настраивать порог микрофона — Gauge vol/thr — сразу видно, слышит ли VAD
  • История фраз — «Что он только что распознал?»
  • Debug — вкладка Code — без Finder/terminal
  • Эстетика Nebula — PhpStorm-splash, mesh, glass — «второй мозг / sci-fi»

Это не замена чату с LLM. Dashboard не отправляет сообщения агенту.

Что мы не забрали в Agent Shell / CMS

  • Отдельная monitor-страница — только /shell/index.html — ❌
  • Gauge vol/thr — нет метрик микрофона в API — ❌
  • phrase_history — ❌
  • Вкладка Code (raw status) — ❌
  • Nebula фон (mesh, hex, neon) — горы + glass — ❌
  • Опрос 500 ms — SSE /api/shell/stream — ⚠️ частично
  • Battery ring — ❌
  • Mock prompt + nav — в Shell prompt реальный (QwenPaw) — ✅ лучше
  • serve_dashboard.sh :8844 — всё через CMS :3000 — ⚠️ страница /shell/monitor.html могла бы быть позже

Главное не забранное по смыслу: не картинка Nebula, а роль «Voice Console / Monitor» — второй экран для отладки и наблюдения за голосом.

Как это ложится на Agent Shell

dashboard → GET /api/shell/status + SSE
          → (позже) GET /api/shell/metrics  // vol, thr
          → thread для history фраз
  • voice_status.txt → state.phase, state.phrase, qwenpaw.ok
  • phrase_history.json → последние N STT-фраз или thread
  • vol/thr gauge → новое поле в sidecar → API

Agent Shell = действие (говорить, отправить, ответ). Nebula Dashboard = наблюдение (слушает ли, что распознал, сырой статус). CMS — большой UI редактора; Nebula был третьим экраном только для голоса.

Нужен ли сейчас?

  • Да — если отлаживаете sidecar / «не распознано», второй монитор, vol/thr
  • Нет срочно — если хватает pulse + фразы в Shell

Итог: dashboard_nebula.html — живая панель мониторинга голосового пайплайна Aya (статус, gauge, история, debug), в стиле Nebula; не чат и не управление. В Agent Shell забрали компактный бар, но не забрали идею отдельной Voice Console — логично как /shell/monitor.html поверх /api/shell/*, когда появятся метрики sidecar.

TODO · датчики · что имеет смысл для Agent Shell

Mac ≠ iPhone. На MacBook есть аксelerometр (внутренний), датчик света, lid, Touch ID, камера/микрофон. На iMac / mini / Studio — почти нет motion-датчиков. Гироскопа, компаса, GPS, TrueDepth на Mac нет. В браузере / Electron DeviceOrientation на macOS по сути не работает.

Идея Mac iPhone
«Наклони устройство — UI реагирует» ❌ почти бесполезно ✅ да
«Уронили / резко двигают ноутбук» ⚠️ только нативно (не web) ✅
Камера, микрофон, экран ✅ уже есть в Shell ✅
Геолокация ⚠️ грубо по Wi‑Fi ✅ точнее
Расстояние до лица (TrueDepth) ❌ ✅
Ориентация в пространстве (devicemotion) ❌ web API недоступен ✅ с permission

Вывод для Shell на Mac: камера, микрофон, экран, clipboard, окно Electron — основные «входы». Ориентация / tilt — сценарий iPhone как второй клиент, не desktop Shell.

  • Mac Shell: не планировать UI на deviceorientation
  • iPhone PWA / app: DeviceMotion + permission → события в CMS/QwenPaw
  • Capabilities manifest: разные наборы для macOS vs iOS
TODO · маркеры vs метки (дословно из чата)

Понял разницу:

Тип Пример Смысл Что с ним делать
Маркер замены {{tpl:brief}} «подставь инструкцию» Развернуть для агента, в чате показать исходник
Метка структуры [tts-break], ```awn-stt``` «здесь граница блоков» Не трогать, всегда видна в чате

Ниже — варианты, как это можно было бы оформить по-другому, чтобы путаницы не было.

1. Разные синтаксисы (самое наглядное)

Вариант Замена (compose) Метка (структура) Плюсы Минусы
A. Сейчас {{tpl:brief}} [tts-break], ```awn-stt``` BBCode для голоса, {{…}} — параметры и шаблоны Два семейства синтаксиса
B. Разные скобки [[tpl:brief]] или @brief {{shell:voice-end}} Сразу видно: «это другое» Два формата в голове
C. Префикс-команда /brief в начале строки --- voice-end --- Как slash-команды в чатах Сложнее парсить в markdown
D. HTML-like <cmd tpl="brief"/> <voice-end/> Явно «тег vs команда» Некрасиво в plain text

2. Разное поведение при отправке (один синтаксис, разные правила)

Правило tpl:* shell:* В чате Агенту
Expand-on-send ✅ заменить на текст ❌ не трогать Оба как в compose tpl → текст, shell → как есть
Expand + chip ✅ + chip «было: brief» ❌ Chip под сообщением Как выше
Dual storage хранить raw + expanded только raw Всегда raw expanded для API · Лучше для «восстановить потом»
Toggle в UI «Показать развёрнутое» всегда метка Переключатель Без изменений

3. Разные namespace / префиксы (логика в имени)

Namespace Семантика Пример Поведение
tpl: шаблон → замена {{tpl:brief}} expand
shell: системная метка {{shell:voice-end}} passthrough
page: контекст страницы {{page:current}} expand (скрытый блок)
var: переменная сессии {{var:last_topic}} expand

Идея: по префиксу код знает: «заменять или оставить».

4. Как показывать в чате (чтобы не потерять смысл)

Подход Замена {{tpl:brief}} Метка {{shell:voice-end}}

5. Что я бы рекомендовал (если переделывать «чисто»)

Роль Синтаксис Отправка В чате
Шаблон (замена) {{tpl:brief}} → текст из settings всегда маркер, expanded — по клику
Метка (структура) [tts-break] как есть разделитель, не удалять
Правило в коде tpl:* = expand shell:* = passthrough

То есть не один «маркер на всё», а два класса:

{{tpl:*}}     → macro (макрос, подставляется)
{{shell:*}}   → marker (метка, остаётся)

6. Альтернатива: вообще убрать замену из текста

Вариант Как работает Плюс Минус
Chips над полем шаблоны не в тексте, а badges над compose В тексте нет «исчезающих» маркеров Не видно в копируемом тексте
Отдельное поле API message + instructions[] Чистое разделение Сложнее UI и протокол
Системный prompt шаблоны → в system, не в user message История чата чистая Меньше контроля «на это сообщение»

Кратко: проблема не в {{…}} как таковых, а в том, что один формат смешивает два разных смысла. Либо развести синтаксис (tpl vs shell), либо развести поведение (expand vs passthrough) и всегда хранить raw в чате, а expanded — отдельно или по клику.

Если скажешь, какой столбец из таблицы ближе (B — разные скобки, dual storage, chips без текста и т.д.), можно спроектировать это точечно под Shell.

Mac-приложение: npm run shell:dist, затем npm run shell:open

            Очередь сохранения сообщений и голосовых

            Сейчас очередь в Voice работает только при связи с сервером (Mac / Agent CMS). Задача — не терять набранный текст и голосовые при обрыве сети и догонять отправку, когда связь вернётся (как исходящие в Telegram, но на нашей базе).

            Что уже есть

            • Очередь на сервере — enqueueShellMessage, файлы awn-dialogs/…/queue/*.json.
            • UI очереди — блок «сейчас» + ожидающие, редактирование и удаление pending через /api/shell/queue.
            • Несколько сообщений подряд — пока агент занят, кнопка «В очередь · N»; каждая отправка — POST /api/shell/message (ответ 202 accepted).
            • Голос после STT — тот же путь, что и текст (voice: true).

            Чего не хватает (суть задачи)

            • Клиентский outbox — сначала сохранить локально, потом отправить при online / успешном apiFetch; серверную очередь не дублировать логикой, а подключать после доставки на CMS.
            • Текст — localStorage или IndexedDB: pending → тот же POST → удалить при успехе.
            • Голос — сложнее: blob + метаданные локально, при сети STT как сейчас → POST; либо отложенная загрузка аудио, если появится endpoint.

            Если «нет интернета»

            • Нет связи с сервером Voice (Failed to fetch) — в дисковую очередь ничего не попадает; текст может мелькнуть только в памяти вкладки. Черновик compose тоже на сервере.
            • Сервер есть, модель недоступна — сообщения уже в очереди на диске; при ошибке модели элемент снимается с ошибкой (message_error), это не «ждёт сеть», а сбой хода.

            Ограничение: без доступа к Mac/CMS агент всё равно не ответит — outbox спасает ваши сообщения, а не работу без сервера. Реализация в основном на клиенте; сервер уже умеет принимать очередь.
